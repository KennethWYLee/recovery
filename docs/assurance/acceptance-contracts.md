# Continuity Ops 驗收契約

文件版本：`1.0.0`  
產品基準：Continuity Ops `2.2.0`、API `2.2.0`、schema `0004`  
文件狀態：現行需求基準；各契約的執行證據狀態另列，不把規格當成測試結果。

## 1. 目標使用者與問題

Continuity Ops 提供單一組織的 IT 維運、SRE、資安應變、服務負責人、事件指揮及稽核人員使用。它要解決的問題是：服務異常時，團隊常在多個工具與對話之間分散資訊，無法清楚確認誰負責、目前判斷、已採取措施、能否結案，以及事後如何追溯。

系統以一筆事件作為共同工作紀錄，讓有權限的人員完成下列工作：

- 建立服務與事件，指派事件角色；
- 依允許順序推進事件狀態；
- 保存調查、緩解、驗證、工作項目與對外說明；
- 在完成條件不足時拒絕結案；
- 保留版本、時間軸、稽核與問題代碼，供重試、診斷與事後檢討。

## 2. 本版本範圍

本版本包含單一組織、角色權限、服務目錄、事件生命週期、事件角色、工作項目、時間軸、驗證證據欄位、通訊審核狀態、事後檢討、稽核紀錄、冪等寫入、版本衝突控制與組織時區。

本版本明確不包含：

- 外部狀態頁、Email、簡訊或聊天平台的實際傳送與送達回執；
- 真實監控資料、SLO 數據、告警觸發或值班通知的匯入；
- 多組織租戶管理、附件上傳、資料匯出 API，以及服務生命週期歷程以外清單的 cursor pagination；
- WebSocket 或其他即時推播；目前介面使用週期性查詢；
- 已完成的正式身分整合、遠端備份還原、災難復原、production 容量／壓力／長時間穩定性測試、獨立資安查核或完整無障礙符合性；
- 已完成的外部專業使用者可靠性結論。

## 3. 判定原則

- 「畫面上有按鈕」不等於完成；伺服器與資料庫必須接受正確操作並拒絕不正確操作。
- 「有 HTTPS 網址」只證明欄位格式與保存符合契約，不代表系統已讀取或驗證網址內容。
- 系統內的 `published` 只表示已完成內部審核及標記發布，不表示外部管道已傳送或送達。
- 沒有真實遙測時，服務狀態必須顯示未知，不能因為沒有事件就推論正常。
- 所有成功率都要保留分母、排除規則與失敗資料；不能只報成功案例。

|---|---|---|---|---|
| AC-001 | 已驗證身分進入系統 | 本機只接受明確設定的操作員；正式環境只接受受信任身分邊界轉送的 Email；使用者及組織會員資格皆為啟用狀態時才建立操作情境。 | 未登入回傳 401；只有身分但未受邀者回傳 403，且不能因此自動取得會員資格。 | `verified_local`：授權單元、API 與 caller-supplied 身分 header 不能取代設定中本機 actor 的 agent 黑箱案例通過；完整 production 身分邊界仍為 `not_verified`。 |
| AC-002 | 組織管理員、指揮官、應變人員、觀察者或稽核人員操作 | 每個角色只取得明確列出的權限；事件回應還要符合事件內指派角色；組織角色只能持有相容的事件角色。 | 不能只靠隱藏前端按鈕；未授權 API 請求必須回傳 403；不相容事件指派被拒絕；仍有不相容啟用指派時不能先降權或停用；最後一位管理員不得被停用或降級。 | `verified_local`：37/37 單元、0001→0004 migration、Gherkin 選定情境、18/18 故障注入及指定 Worker API 負例通過；正式身分邊界未驗證。 |
| AC-003 | 管理服務目錄 | 可建立服務，固定 slug，設定層級、負責人、SLO 目標、Runbook HTTPS 網址與狀態；更新使用 `expectedVersion`；每次淘汰或重新啟用都要明確確認，保存 8–1000 字原因、合格操作者、request ID 與時間，並新增不可改寫的生命週期事件；有權限者使用 HMAC-SHA256 簽章且綁定組織與服務的 keyset cursor，依穩定順序分批讀取完整歷程。 | 重複 slug、變更 slug、無效 SLO、非啟用成員負責人、舊版本更新、未確認、缺少理由、只有空白變形的理由、缺 request ID、不合格操作者、無狀態變更卻改寫 metadata、改寫／刪除歷史事件、無效／重複／變造／跨範圍 cursor，以及仍有未結案事件的服務淘汰均被拒絕。 | `verified_local`：0004 migration、簽章 cursor 單元案例、指定 Worker API 正反例與多頁歷程通過；內部桌面瀏覽器已核對分頁與確認介面。遠端、行動裝置與獨立 QA 未驗證。 |
| AC-004 | 宣告事件 | 有權限者可為啟用服務建立事件，取得唯一事件編號、初始 `declared` 狀態、時間軸與稽核紀錄。 | 不得為無效或已淘汰服務建立事件；同一冪等請求重送不得建立第二筆事件。 | `verified_local`：Gherkin 選定情境與指定 Worker API smoke 通過；正式環境未驗證。 |
| AC-005 | 指派或交接事件角色 | 指揮者可指派啟用會員；事件指揮官必須同時具有組織 `admin` 或 `commander` 角色；撤銷保留歷史。 | 未提供合格接任者時，不得撤銷未結案事件最後一位指揮官；交接必須在同一批次完成。 | `verified_local`：2.2.0 授權、migration 與指定 Worker API smoke 通過。 |
| AC-006 | 推進事件狀態 | 只有具組織權限且符合事件指派的人可依狀態圖推進；版本、里程碑時間、時間軸與稽核同步更新。 | 越級、非法倒退、舊版本、無事件角色或權限不足的轉換均被拒絕。 | `verified_local`：授權、領域、migration、Gherkin、指定 Worker API smoke 與 18/18 風險導向故障注入通過；不是完整 mutation testing。 |
| AC-007 | 記錄調查、緩解或驗證 | 事件時間軸可保存事件類型、訊息、操作者、request ID；驗證資料可另存 HTTPS 參考、來源名稱、觀測起訖與 SHA-256。 | 非 HTTPS、觀測時間顛倒或錯誤 digest 被拒絕；時間軸及稽核列不能更新或刪除。 | `verified_local`：2.2.0 migration 與指定 Worker API smoke 通過；外部證據內容正確性未驗證。 |
| AC-008 | 建立及完成事件工作 | 應變人員可建立工作、指定負責人、期限、優先度與狀態；`completed` 必須保存合法 HTTPS 證據。 | 完成時缺少合法證據被拒絕；曾為 critical 的工作取消時必須保存 8-1000 字理由，不能用同一請求先降級再規避。 | `verified_local`：領域、migration、Gherkin 選定情境與指定 Worker API smoke 通過。 |
| AC-009 | 撰寫事件通訊 | 合格人員建立 `draft`，授權人員另行審核成 `reviewed`，再另行標記 `published`；外部受眾須有未來更新時間或以 `[FINAL]` 開頭的最終訊息。 | 未審核直接發布、核准後改寫內容、已發布後更新／刪除、過期排程或事件結束後發布均被拒絕。 | `verified_local`：migration、Gherkin 選定情境與指定 Worker API smoke 通過；外部送達不在範圍。 |
| AC-010 | 將事件從 monitoring 改為 resolved | 必須同時有非空白驗證準則、本次進入 monitoring 後新增的 verification，以及沒有未完成 critical 工作。 | 缺少任一條件時回傳可辨識問題代碼；前一次 monitoring 週期的舊證據不能通過。 | `verified_local`：2.2.0 migration 與指定 Worker API smoke 通過。 |
| AC-011 | 完成事後檢討或重新開啟事件 | 只有 resolved／closed 事件可建立檢討；草稿可不完整，完成版必須填妥六段；重新開啟會將完成版回到草稿並保留紀錄。 | 未解決事件、未填妥完成版、舊版本更新不得通過；重新開啟不能保留錯誤的「已完成」狀態。 | `verified_local`：2.2.0 migration 與指定 Worker API smoke 通過。 |
| AC-012 | 使用者因逾時重送寫入請求 | 每個 mutation 使用 8-128 個可見 ASCII 字元的 Idempotency-Key；相同組織、操作者、操作範圍、key 與 payload 重送得到相同結果。 | 同一 key 搭配不同 payload 回傳 409；重送不能重複建立資料；過期回執清理不能跨組織。 | `verified_local`：migration、stateful retry，以及兩個同時且相同的冪等請求只建立一筆資料並重播同一結果；正式清理監控未驗證。 |
| AC-013 | 兩位操作員同時修改同一資料 | 服務、事件、會員、工作、通訊與檢討更新使用 `expectedVersion`；成功時版本加一。 | 舊版本不能覆寫新版本，必須回傳 409；高風險不變條件由 API 與 D1 共同保護。 | `verified_local`：migration 與兩個同版本並行更新的一勝一衝突案例通過；正式遠端競爭與中途故障未驗證。 |
| AC-014 | 操作成功或被拒絕後追查 | 成功 mutation 保存 actor、角色、操作、資源、request ID、結果與時間；可判定的拒絕／失敗在有可信 actor 後保存不含 payload 的稽核資料；每個 API 回應帶 request ID。 | request telemetry 不得含 request body、cookie、token、Authorization 或使用者自由文字；時間軸與稽核不能改寫。 | `verified_local_controlled`：最終本機 Log 為 815/815 有效，其中 54 筆為受控 4xx、5xx 為 0；安全負向檢查的 request ID 對應為 44/44，API／schema／deployment version 均一致。正式收集、告警與保存為 `not_verified`。 |

## 5. 核心流程完成定義

一條完整事件處理流程至少要能由合格操作者完成：建立服務、宣告事件、指派角色、推進調查與緩解、建立工作、保存完成證據、撰寫並審核通訊、進入 monitoring、新增本週期驗證、通過三項結案條件、解決事件、完成事後檢討。每一步都必須能從 API 結果、資料狀態、時間軸或稽核紀錄核對。

這項完成定義不包含外部通訊送達、真實服務恢復或外部使用者穩定完成的結論；這些要以另外的整合及外部證據判斷。
