# Continuity Ops 設計決策紀錄

文件版本：`1.0.0`  
狀態：依目前實作回溯整理。每則紀錄說明既有決策，不代表所有後續驗證已完成。

## ADR-001：單一組織的事件指揮工作區

- 狀態：已採用。
- 情境：目前產品服務一個具共同治理、身分與資料邊界的維運組織。
- 決定：使用固定 organization context，所有主要資源保存 `organization_id`，會員資格決定組織存取。
- 未採用方案：在第一版加入多租戶切換、跨組織分享與租戶自助建立。
- 理由：先把事件生命週期、資料一致性與權限做完整；多租戶會增加隔離、計費、管理及測試面積。
- 後果：目前不能宣稱支援多組織 SaaS。日後加入多租戶前，所有查詢、唯一索引、冪等、稽核、備份與 Log 都要重新檢查租戶隔離。

## ADR-002：伺服器端組織權限、事件角色與相容矩陣

- 狀態：已採用。
- 情境：組織角色不等於每一事件的實際職責，前端隱藏操作也不能阻止直接 API 請求。
- 決定：先檢查組織 permission，再檢查事件內 assignment；事件角色不能擴張組織權限，並由共用相容矩陣限制可指派組合。資料庫拒絕不相容指派，也拒絕會留下不相容 active assignment 的會員降權或停用。
- 未採用方案：只用單一全域角色，或只在 UI 判斷權限。
- 理由：符合最小權限，也能保留每次事件的責任分工。
- 後果：授權案例較多；每個新 endpoint 都要同時檢查組織與資源關係，並加入正反例。

## ADR-003：寫入採冪等、樂觀鎖定及原子 batch

- 狀態：已採用。
- 情境：事件期間常有網路逾時、重試及多人同時操作。
- 決定：mutation 必須帶 Idempotency-Key；相同 key 綁定 canonical request hash；可修改資源帶 `expectedVersion`；業務更新、時間軸、稽核與回執放入同一 D1 batch。
- 未採用方案：由前端禁止重複點擊、最後寫入者覆蓋、每筆資料分開寫入。
- 理由：前端無法防止傳輸重試或並行；事件紀錄不能接受無聲覆寫與部分成功。
- 後果：用戶端要處理 409，回執要有界清理；正式環境仍需監控回執容量與衝突率。

## ADR-004：重大資料規則由 API 與 D1 共同保護

- 狀態：已採用。
- 情境：只在 UI 或 handler 檢查，可能被並行請求、日後程式錯誤或直接 SQL 繞過。
- 決定：API 提供清楚問題代碼，D1 再以 foreign key、check、unique index、trigger 與 write guard 保護事件轉換、版本、結案、指派、通訊、工作與 append-only 紀錄。
- 未採用方案：只使用應用程式驗證。
- 理由：高風險不變條件需要最後一道資料層保護。
- 後果：migration 較複雜；必須測空白安裝、legacy 升級與直接 SQL 負例，並維持 Drizzle schema 對照。

## ADR-005：事件解決採三項必要條件

- 狀態：已採用。
- 情境：只按「解決」容易讓事件在缺少復原判定或重要工作未完成時結案。
- 決定：`monitoring → resolved` 同時要求驗證準則、本次 monitoring 週期後的 verification，以及沒有未完成 critical 工作。
- 未採用方案：只由事件指揮官主觀確認，或只要求一筆任意時間的驗證紀錄。
- 理由：讓結案可以被系統判定與事後查核，並避免舊證據誤用。
- 後果：操作者要先維護驗證準則與時間軸；系統仍不判斷外部證據內容是否真實。

## ADR-006：通訊的 `published` 只代表內部狀態

- 狀態：已採用。
- 情境：產品目前沒有狀態頁、Email 或訊息平台 connector，也沒有送達回執。
- 決定：以 draft、reviewed、published 保存內部審核流程；不觸發外部傳送。
- 未採用方案：用假按鈕或成功提示模擬已送達。
- 理由：避免系統對外部行為做無證據承諾。
- 後果：操作與文件必須清楚說明限制；加入 connector 時要新增整合狀態、重試、失敗、冪等及送達證據。

## ADR-007：沒有服務遙測時顯示未知

- 狀態：已採用。
- 情境：事件資料不能代替真實監控指標；零事件也不能證明服務正常。
- 決定：沒有外部遙測時回傳 `unknown`、`unavailable`、樣本數 0 與 null SLO attainment。
- 未採用方案：根據事件數推論綠色健康狀態或填入示範數值。
- 理由：缺資料時不做過度推論。
- 後果：畫面可能較不「完整」，但不會製造假健康；日後須為真實 telemetry 定義來源、時間窗、品質與失效語意。

## ADR-008：本機身分與正式身分分開

- 狀態：已採用；正式邊界待驗證。
- 情境：開發環境需要可重現操作員，正式環境必須信任受保護的身分代理。
- 決定：localhost 只接受明確環境設定的 local operator；非本機只接受 forwarded verified Email，且只有既有會員或明確 bootstrap admin 可建立 actor。
- 未採用方案：使用任意 request header、query string 或自動註冊所有已驗證 Email。
- 理由：避免測試捷徑成為正式環境後門。
- 後果：正式部署必須證明上游會移除用戶端偽造 header，並安全管理 bootstrap 設定。

## ADR-009：週期性查詢而非即時推播

- 狀態：已採用。
- 情境：事件工作區需要更新，但目前沒有 WebSocket、SSE 或訊息匯流排。
- 決定：事件明細約 8 秒、總覽約 30 秒輪詢，頁面重新可見時立即查詢。
- 未採用方案：在沒有完整連線、重試與授權設計前宣稱即時推播。
- 理由：在現有架構下保持簡單、可理解且可降級。
- 後果：存在可量測延遲及額外讀取；文件與測試不得使用「即時」描述，規模增加時須評估負載與 backoff。

## ADR-010：UTC 保存與組織 IANA 時區輸入

- 狀態：已採用。
- 情境：事件、期限及通訊排程跨時區，DST 會產生不存在或重複的地方時間。
- 決定：組織保存 IANA 時區；介面以組織地方時間輸入，轉成 UTC instant 保存；無效設定採 UTC；模糊或不存在時間拒絕。
- 未採用方案：保存未帶時區的字串，或在 DST 模糊時任選一個結果。
- 理由：避免無法追溯的時間偏移。
- 後果：輸入可能被拒絕並要求改時間；跨時區瀏覽器與正式 D1 round-trip 仍要補完整證據。

## ADR-011：時間軸與稽核紀錄 append-only

- 狀態：已採用。
- 情境：事件調查需要知道當時誰做了什麼，事後改寫會破壞可信度。
- 決定：時間軸與稽核列只能新增，D1 trigger 拒絕更新與刪除；修正以新事件說明。
- 未採用方案：允許管理員直接改寫歷史。
- 理由：保留原始決定與更正路徑。
- 後果：資料量持續增加；仍需保存、封存、合法刪除與備份政策，append-only 不是無限保存的法律依據。

## ADR-012：證據狀態與發布決定分開

- 狀態：已採用於本套保證文件。
- 情境：原始碼存在、測試通過、本機驗證、外部驗證及正式核准是不同主張。
- 決定：使用 `source_confirmed`、`verified_local`、`planned_template`、`not_verified` 等明確狀態；清單不自動等於發布核准。
- 未採用方案：將計畫、截圖、測試檔或工具綠燈統稱為「已完成」。
- 理由：讓委員、QA 與發布決定人能看見證據範圍與限制。
- 後果：尚未驗證的項目必須保留為缺口，即使產品介面看起來完整。

## ADR-013：服務狀態變更保存理由、操作者與時間

- 狀態：已採用於 schema 0004。
- 情境：只保存 active／deprecated 無法說明為何淘汰或重新啟用，也無法判斷決定是否由合格人員做出。
- 決定：每次狀態改變要求專用確認、8–1000 字理由、目前啟用的 admin／commander actor、request ID 與 UTC 時間；API 拒絕未確認，D1 將換行、歸位、tab、vertical tab、form feed 與 NBSP 納入空白判定。trigger 同時新增 append-only 生命週期事件，狀態未改時不能另外改寫 metadata。舊淘汰列缺少歷史理由時明確顯示為 legacy，不補造不存在的理由。
- 未採用方案：只在前端確認視窗顯示理由、讓管理員事後補寫歷史理由，或從 audit 猜測理由。
- 理由：讓生命週期決定可追溯，同時保持歷史證據誠實。
- 後果：服務更新 API 與 UI 要處理專用欄位；migration 與 smoke 必須同時驗證淘汰、重新啟用、錯誤 actor、改寫及 legacy 資料。

## ADR-014：服務生命週期歷程使用穩定的 keyset 分頁

- 狀態：已採用於 2.2.0；單元、指定本機 API artifact 與同一 digest 的內部桌面分頁／確認介面已驗證，行動裝置、遠端與獨立 QA 仍待驗證。
- 情境：生命週期事件不可改寫且會持續增加。一次回傳無上限資料會增加延遲與資源風險；固定截斷又會讓使用者誤以為已看到全部歷程。
- 決定：依 `changed_at DESC, id DESC` 排序，每次最多回傳 25 筆；多讀一筆判斷是否還有資料。下一頁使用包含時間與 ID、HMAC-SHA256 簽章且綁定 organization 與 service 的版本化 opaque base64url cursor；secret 缺漏或少於 32 字元時 fail closed。cursor 另有長度、字元、欄位與 UTC 時間格式檢查，查詢仍以 organization 與 service 範圍授權。
- 未採用方案：無上限讀取、只回傳最近固定筆數、offset 分頁，或把資料庫內部 row offset 暴露給用戶端。
- 理由：`(changed_at, id)` 提供穩定且明確的邊界；新增較新的事件不會改變既有下一頁的較舊資料位置。
- 後果：API 與 UI 要處理 `hasMore`、`nextCursor`、載入更多、失敗重試與無效 cursor；單元測試要包含 round-trip、變造、過長及非標準輸入，端對端仍須驗證多頁、不重複、不漏資料與授權隔離。
